# Service Provider Registration — Fix & Redesign

**Date:** 2026-04-27
**Status:** Design — pending implementation plan
**Repos affected:** `Service_Provide` (RN app), `dribee-web-monorepo/backend` (API)

---

## 1. Problem

Service provider registration in the `Service_Provide` app does not work. The frontend collects a partial set of fields and sends a payload that the backend register schema rejects at validation. After the (failing) request the FE also auto-authenticates the user — which is wrong because login should only be possible **after admin approval**.

In addition, the backend `pro` table and surrounding registration/approval flow have several latent bugs and missing data (KYC, address, machine types) that must be fixed alongside the FE work.

## 2. Goals

- Self-registration flow that collects: name, phone, email, skills (= service types), service zones, machine types, address, KYC (Aadhaar last 4 + PAN + ID proof image), bank details.
- Submission creates a `pending` external pro that the admin reviews.
- After admin approval (with a password set by admin), the user can log in. Until then they cannot.
- Source-of-truth for skills/zones/machine-types/states/cities is the master data API.
- KYC, address, bank are stored as queryable columns (not buried in JSONB) on approval.
- The provider never enters Razorpay IDs — those are generated by the backend on approval and used for payouts.

## 3. Non-Goals

- Pro profile editing post-registration (existing endpoints already cover this).
- Admin UI changes (existing approve/reject endpoints used as-is).
- Migration / cleanup of any pros already in the database.
- Multi-country support (assume India: states + cities only).

## 4. Roles & Registration Type

- Self-registered providers create rows with `registration_type = 'external'`.
- Admin-created providers (existing flow, untouched) use `registration_type = 'in_house'`.
- The user role assigned on approval is the existing `'pro'` role (looked up from the `roles` table).

## 5. Database Schema

### 5.1 Final `pros` table

```sql
CREATE TABLE pros (
  id                       BIGSERIAL PRIMARY KEY,
  user_id                  BIGINT       NOT NULL REFERENCES users(id),

  name                     VARCHAR(150) NOT NULL,
  phone                    VARCHAR(20)  NOT NULL,
  email                    VARCHAR(255),

  registration_type        VARCHAR(20)  NOT NULL
    CHECK (registration_type IN ('in_house','external')),

  status                   VARCHAR(20)  NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','active','rejected','inactive')),

  -- Address (state_id, city_id from master)
  address_line1            VARCHAR(255) NOT NULL,
  address_line2            VARCHAR(255),
  state_id                 BIGINT       NOT NULL REFERENCES states(id),
  city_id                  BIGINT       NOT NULL REFERENCES cities(id),
  pincode                  VARCHAR(10)  NOT NULL,

  -- KYC (NOT NULL — required at registration)
  aadhaar_last4            CHAR(4)      NOT NULL,
  pan_number               VARCHAR(10)  NOT NULL,
  id_proof_url             VARCHAR(500) NOT NULL,

  -- Bank
  bank_account             JSONB        NOT NULL,

  -- Payouts (auto-generated on approval; nullable until then)
  razorpay_contact_id      VARCHAR(100),
  razorpay_fund_account_id VARCHAR(100),

  -- Approval workflow
  rejection_reason         TEXT,
  approved_by              BIGINT REFERENCES users(id),
  approved_at              TIMESTAMP,

  -- Operational
  is_available             BOOLEAN      NOT NULL DEFAULT true,

  created_at               TIMESTAMP    NOT NULL DEFAULT now(),
  updated_at               TIMESTAMP    NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX uq_pros_user_id ON pros(user_id);
CREATE INDEX idx_pros_phone   ON pros(phone);
CREATE INDEX idx_pros_status  ON pros(status);
CREATE INDEX idx_pros_city_id ON pros(city_id);
```

Removed from previous schema: `max_jobs_per_day`, `commission_pct`. (If used elsewhere, reintroduce; otherwise drop.)

`bank_account` JSONB shape: `{ accountNumber: string, ifsc: string, holderName: string, bankName: string }`.

### 5.2 Junction tables (existing — confirm structure)

- `pro_skills(pro_id, service_type_id)` ← from `serviceTypeIds[]`
- `pro_zones(pro_id, zone_id)` ← from `zoneIds[]`
- `pro_machine_types(pro_id, machine_type_id)` ← from `machineTypes[]` (currently NOT populated on approval — fix in approval flow)

### 5.3 `pro_registration_requests` table

Already has `payload_json`, `status`, `reviewed_by`, `reviewed_at`, `created_at`, `rejection_reason`. Add:

- Unique partial index: `CREATE UNIQUE INDEX uq_proreg_phone_pending ON pro_registration_requests((payload_json->>'phone')) WHERE status = 'pending_approval'`
  to prevent duplicate pending submissions for the same phone.

### 5.4 `states` and `cities` master tables

If they don't already exist:

```sql
CREATE TABLE states (
  id   BIGSERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE,
  is_active BOOLEAN NOT NULL DEFAULT true

CREATE TABLE cities (
  id        BIGSERIAL PRIMARY KEY,
  state_id  BIGINT       NOT NULL REFERENCES states(id),
  name      VARCHAR(100) NOT NULL,

CREATE INDEX idx_cities_state_id ON cities(state_id);
```

## 6. Backend API Changes

### 6.1 Master endpoints

- `GET /v1/master/states` → `{ id: number, name: string }[]` (active only).
- `GET /v1/master/cities?stateId=:id` → `{ id, name, state_id }[]` (active only, filter by `state_id`).
- `GET /v1/master/machine-types` — fix to filter by `is_active = true` (currently returns all).
- `GET /v1/master/service-types` — already correct.
- `GET /v1/master/zones` — already correct.

### 6.2 ID-proof upload (new, public)

`POST /v1/service/pros/upload-id-proof`

- Public (no auth — provider isn't logged in yet during registration).
- Multer: max 5 MB, accepts `image/jpeg`, `image/png`, `application/pdf`. Field name: `idProof`.
- Response: `{ url: string }` — the URL the FE will pass back as `idProofUrl` in the register payload.
- Storage: same local-disk pattern used by other multer routes (`/uploads/id-proofs/<filename>`).
- Rate limit: 10 requests / IP / hour to mitigate abuse.

### 6.3 `registerProSchema` changes

In `backend/src/modules/service/service.types.ts`:

- **Remove** `skillTags` (skills are now derived from `serviceTypeIds`).
- **Add** `addressLine1`, `addressLine2?`, `stateId`, `cityId`, `pincode`.
- **Keep** `fullName`, `phone`, `email?`, `aadhaarLast4`, `panNumber`, `idProofUrl`, `bankAccountNumber`, `ifscCode`, `serviceTypeIds[]` (UUIDs, min 1), `machineTypes[]` (string[] of machine type names, min 1), `zoneIds[]` (UUIDs, min 1).

### 6.4 Approval flow (`approveProRegistration`)

In `backend/src/modules/service/service.repository.ts`:

1. Look up role `'pro'` (existing).
2. Insert into `users` with admin-supplied password (existing).
3. **Insert into `pros`** with `registration_type = 'external'`, status `'active'`, copying from `payload_json`:
   - identity (`name`, `phone`, `email`)
   - address (`address_line1`, `address_line2`, `state_id`, `city_id`, `pincode`)
   - KYC (`aadhaar_last4`, `pan_number`, `id_proof_url`)
   - bank (`bank_account` jsonb)
4. Insert into `pro_skills` from `serviceTypeIds`.
5. Insert into `pro_zones` from `zoneIds`.
6. Insert into `pro_machine_types` from `machineTypes` (currently missing — fix).
7. Call Razorpay Contacts API → store `razorpay_contact_id`.
8. Call Razorpay Fund Account API with bank details → store `razorpay_fund_account_id`.
9. Mark `pro_registration_requests.status = 'active'`, set `reviewed_by`, `reviewed_at`.

If Razorpay calls fail, the approval transaction rolls back and the admin sees the error. (Alternative: store pro as `active` with null Razorpay IDs and retry later — to be decided in the implementation plan.)

## 7. Frontend (Service_Provide RN app)

### 7.1 Wizard structure (`RegisterScreen.tsx`)

Three steps, single submit at the end. Progress indicator at the top.

**Step 1 — Basic info**
- `fullName` (required, 2–80)
- `phone` (required, 10 digits, India)
- `email` (optional, valid email if provided)

**Step 2 — Services**
- `serviceTypeIds[]` (chip multi-select, min 1) — `useServiceTypes()`
- `zoneIds[]` (chip multi-select, min 1) — `useZones()`
- `machineTypes[]` (chip multi-select of machine type **names**, min 1) — new `useMachineTypes()`

**Step 3 — Address, KYC, Bank**
- Address: `stateId` (dropdown via `useStates()`) → `cityId` (dropdown via `useCities(stateId)`, disabled until state selected) → `addressLine1`, `addressLine2`, `pincode`
- KYC: `aadhaarLast4` (4 digits), `panNumber` (10-char regex `[A-Z]{5}[0-9]{4}[A-Z]`), ID-proof image picker
- Bank: `holderName`, `accountNumber` (9–18 digits), `ifsc` (11-char regex), `bankName`

ID-proof flow: user picks image → FE calls `POST /v1/service/pros/upload-id-proof` → stores returned URL in form state. Submit blocks until upload completes.

### 7.2 Validation

Single Zod schema `registerProSchema` in `src/utils/validations/index.ts` mirroring the backend schema (per `CLAUDE.md`). All field-level validation goes through this schema; the wizard validates **only the current step's slice** of the schema before allowing "Next".

### 7.3 Submission

- Upload ID proof first; on success, store `idProofUrl`.
- POST `/service/pros/register` with backend field names (`fullName`, not `name`; no `skillTags`).
- Body shape:
  ```ts
  {
    fullName, phone, email?,
    addressLine1, addressLine2?, stateId, cityId, pincode,
    aadhaarLast4, panNumber, idProofUrl,
    bankAccountNumber, ifscCode,
    serviceTypeIds, machineTypes, zoneIds
  }
  ```
- On success, **do not** call `setAuthenticated(true)` and **do not** populate `proSlice`. Navigate inside `AuthStack` to `RegistrationSubmittedScreen`.

### 7.4 `RegistrationSubmittedScreen` (replaces existing `PendingApprovalScreen` polling behavior)

- Static screen with messaging: "Your registration has been submitted. The Dribee team will review it and notify you when your account is approved. You'll then be able to log in with credentials provided to you."
- Single CTA: "Back to login" → resets `AuthStack` to `LoginScreen`.
- No polling. Removes the existing 30-second mock poll.

### 7.5 New / changed files

New master query hooks in `src/services/master/master.query.ts`: `useStates`, `useCities(stateId)`, `useMachineTypes`.

Removed: `proSlice.pendingApproval` mock-state machinery and the polling effect in `PendingApprovalScreen`.

### 7.6 Error handling

- Field validation errors → inline under each field (Zod messages).
- Server validation errors (HTTP 400) → toast with `getApiErrorMessage(err, 'Registration failed')`.
- Duplicate phone (HTTP 409 from unique index) → toast: "A registration with this phone number is already pending approval."
- ID-proof upload failures → inline error under the file picker; submit disabled until upload succeeds.

## 8. Admin Side

No new UI work assumed. Confirm during implementation that the existing admin "Pending Pros" list reads `pro_registration_requests` and that the approve modal already collects a password and posts to `PUT /pro-registrations/:id/approve`. If anything is missing, scope it in the implementation plan.

## 9. Out of Scope / Future

- Email/SMS notifications to provider on submission and on approval/rejection.
- Document re-upload after rejection (currently the provider would have to re-register from scratch).
- Multi-language UI for the wizard.
- Profile photo upload at registration time.
